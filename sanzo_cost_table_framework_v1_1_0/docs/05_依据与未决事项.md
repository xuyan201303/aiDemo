# 05｜依据、已知边界与未决事项

## 1. 来源分层

**U1／客户最新依赖详情（用户在本次对话粘贴）**：本期仅①报价导入形成「原価：単価一覧表」；②売上単价及ドレージ料加利、③数量/円建て试算未决定。客户不做費目一覧事前制作和维护；人工纠错后次回同表记自动识别是必需。

**U2／用户确认的使用方案（本次对话）**：案件名+批量附件；同画面单价表/吹き出し编辑；文件位置点击预览；案件一覧、6～10用户和登录；Excel保存下载；新系统是否需别加工待确认。

**U3／用户确认的协作与商业口径（已更新至2026-09-11）**：不另设专门PoC，做商谈Demo；必要时才用同一Demo确认少量实资料，不要求另一个验证系统或必经阶段。Demo及约定范围内的必要资料确认不另收费；正式开发按剩余生产化工作报价。ChatGPTレビュー、Codex有限实现、阶段Review Bundle，以及不改SDK/不干扰批量验证的边界不变。

**U5／用户最新演示与交接指示**：2个Excel＋1个PDF。第1轮上传2份并实际解析、预览、修正保存；第2轮新案件上传第3份，确认同原文表记和条件的分类复用以及新金额读取。島野さん提案结束后请森田さん演示，客户质疑放在Demo后。资料使用提案语气，不代表实动Demo已经完成。

**U4／上传的Markdown「已保存补证结果的有界收尾预览」**：从9,000条case元数据选择64代表、覆盖50 profile/classification族，不是100K验收；复用一次既有finalizer已存输出，没有重新调用SDK/Reference/Comparator或读取原始工作簿（源文件第5～7行）。保留329历史运行字段/父容器缺口；资源预览exit=1和类型结果FAIL不能改成通过（第17、35～37行）。仅用来限制SDK验证状态的表述，不从该文件推断公共API签名或本项目已验证能力。

业务范围以U1/U2为准；演示、商业流程和会议交接以最新U3/U5为准，旧PPT中费用Master请求、新系统别加工主流程、先前报价数字均不沿用为新框架契约。

## 2. 本框架选择，不应冒充客户原话

- 模块化单体、React/TypeScript、Python/FastAPI、PostgreSQL、一套私有存储和worker。
- 精确确认记录优先，未知由AI建议；v1公司范围+完整上下文，不自动跨公司泛化。
- 事务、版本、幂等、历史、冲突与撤销、旧表快照不自动变化。
- UI不增加日常Master维护页；冲突/类别选择在业务吹き出し解决。
- 初期不fine-tuning，不强行上向量数据库、多Agent、Redis或Kubernetes。

以上作为v1实施基线；改变需要说明影响并同步代码/测试/文档，不等于绝对不能调整。
