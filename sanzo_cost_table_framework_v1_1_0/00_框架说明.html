先看这一页

系统只做：报价导入 → 整理并利用过去纠错 → 原価：単価一覧表 → 预览、修改 → 保存并下载Excel。

客户不用先制作费用清单，也不维护另外一张Master。客户在正常业务中修改一次，系统自动保存“原始费用名称 → 客户确认费用”的对应关系，后续条件相同时复用。

做：PDF/Excel/邮件正文导入；单价与条件提取；各费用分类；纠错学习；横向列表；原文预览；当前画面修正；案件管理；6～10人登录及基本用户管理；原价单价表Excel保存与下载。

十条不能走样的规则

  1. 学习的是SDK所对应的原始费目表记 → 人工确认费目，不是“AI错误答案 → 正确答案”。
  2. 本次单价、币种、有效期重新读取，不从旧报价复制。
  3. 同一公司/业务适用范围且条件一致才自动复用；未知条件不是任意匹配。
  4. AI提出的分类不自动变成已确认学习记录；文件里的指令不能成为系统指令。
  5. 普通业务修正即保存学习记录，不要求客户另做Master维护。
  6. 同一键出现矛盾确认、规则被撤销或数据不可靠时，不用AI偷偷选择一个覆盖人工意见。
  7. 预览来自原件及真实来源位置，原件只读；原文找不到要明确显示，不编页码/坐标。
  8. 未分类明细、文件失败、未记载等不能删除或当作0；正常显示也不等于已验证正确。
  9. 学习更新不自动改旧案件或旧Excel；当前修改与学习保存要有事务、版本和幂等保护。
  10. 真实SDK只在适配层接入；不改SDK仓库，不中断其批量测试，不杜撰公共API。

01｜架构与范围

01｜架构与范围

版本：1.0.0。业务范围来自本次对话中的客户补充；技术选型和下述运行策略是本框架的实现决策，尚不是客户签字规格。

1. 产品定位

「海外物流見積の取込・修正学習による原価単価一覧表作成支援」。本期输出成本单价，不计算卖价、利润和数量金额。20/40尺、币种、计费单位等属于单价条件，必须保存；保存条件不等于本期要做换算试算。

“客户不维护费用清单”是强制业务边界；不代表内部不能有费用类别ID和已确认对应关系。第一份资料由系统提出分类；人工只在日常单价表中纠错或确认。不得让客户提供全量费用清单作为开始使用的条件。

2. 构造：模块化单体，不是分布式微服务

正式项目暂定目录名 sanzo-cost-table，与私有 document-processing-sdk 并列且独立。SDK通过固定版本依赖和Adapter调用，默认不使用指向可变工作树的editable安装。

sanzo-cost-table/                 # 后续W1创建的正式项目，当前包不是已部署项目
  apps/
    web/src/
      pages/                     # login, case-create, cost-table, cases, users
      features/review-popover/   # 原地编辑、冲突提示、未保存状态

      api/                       # 由类型契约生成/校验请求响应

      documents/                 # 原件、校验、SDK适配与source blocks
      extraction/                # 费用行/金额/条件抽取和完整性检查
      classification/            # 已确认记录查询、未知AI候选
      learning/                  # 事务保存、适用范围、冲突、撤销
      review/                    # 人工修正与最终确认
      exports/                   # 原价单价表快照与Excel输出

API与worker由同一代码库、同一锁定依赖构建，分别作为进程运行；API受理请求并快速返回任务ID，worker处理耗时文档。前端轮询任务状态即可，初期不必WebSocket。正式运行需要TLS、私有存储、数据库、备份，平台按客户条件决定。

FastAPI可以按模块组织路由，不要求一个功能一套服务；模块划分是本方案设计。[T1]

4. 数据流

4.1 接收与读取

先鉴权、校验上传范围，再私有保存原件并计算内容哈希。文件归属于案件，但一个文件可以有多个报价方案，一个方案也可以来自多个附件；不强制一文件一公司一报价。

SDK读取被置于有限资源worker。记录document_id、原件SHA、SDK版本、解析配置、真实source block ID和原始定位。上传与解析失败必须可见。旧版.xls、.xlsm、带密码或扫描PDF是否支持由真实契约/样本决定，不通过扩展名列表制造已支持的假象；初期输入保留PDF、Excel、邮件正文能力目标，具体条件登记。

4.2 结构化与完整性

已有经过验证的表结构和字段映射可以本地提取。不能可靠确定行、金额、单位关系时调用AI抽取；AI只引用已提供的block IDs，服务器核验block存在且归属一致。AI不得凭空产生页码、坐标和单元格。

每个候选明细区块必须有“纳入明细／非费用且说明理由／未解析”的处置。此清单仅证明已发现候选块均有处置，不能证明解析器发现了原文件每一行；内部功能测试及必要的样本确认还需独立与原件核对漏行。空结果不自动视为成功；除非证据能说明原资料确实无费用。

4.3 分类

从本次已结构化数据取得原始费目名，查询已确认映射。精确命中且无冲突时，分类由程序直接决定。没有可靠记录则由AI参考同租户允许的相关确认案例和已有费目概念提建议。条件未解析的，先回到读取/条件确认，不能用分类AI掩盖条件缺失。

AI抽取调用和AI分类调用分别计数。一个已知费目的分类命中，不意味着这份文件的结构提取没有调用AI；UI和报告不得将分类命中率换算成“整个系统无需AI”。

4.4 单价表与纠错

展示层由报价明细生成，不保存另一套互相脱节的AI表格。客户改名称时关联稳定的fee_id；改条件时只改本次条件，是否生成对应关系需重新校验，不能扩大适用范围。改金额只修改当前报价，不能训练固定价格。

所有字段都可以经合适权限进入纠错，不只是黄色项目。缺失明细可以人工新增，必须标“人工追加”并指向原件依据；不能因原文标签尚未确定就自动创建已确认别名。删除采用排除+理由和历史，不物理丢掉源证据。

4.5 保存与输出

行保存后立即刷新该行和表格版本，同时返回学习效果。生成Excel从特定case_revision建立快照，异步导出只读这个快照；当前页面随后修改不改变旧文件。不存在默认的“再加工”第二步骤。新系统取込转换仅为待确认边界，不算已删除的客户需求也不算已承诺开发。

5. AI与云使用策略

本框架不锁定模型名或OpenAI客户端版本。W0/W2查验真实兼容性后固定具体版本、模型配置、prompt_version、schema_version。普通API不会替应用自动管理客户的持久纠错关系；它们放在自己的数据库中。相关确认案例可作为prompt上下文，属于应用层的记录利用，不等同于模型权重更新。[T2]

计划使用结构化返回，服务器再次校验schema、枚举、来源ID、金额、状态。结构化输出仍可能有内容错误；拒绝、超时、输出截断、无关输入、校验失败分别记录，不转为成功空表。[T3]

实时业务不授予模型网络搜索、代码执行、外部连接器或数据库写权限。客户文件、邮件正文、历史案例都是不可信数据，不得提升为系统指令。发送上下文时保留对费用理解必需的条件，但不发送无关账户、其他租户信息或全部历史报价。

默认 ALLOW_EXTERNAL_AI=false，取得资料使用许可和环境设置后显式启用。SDK内可能存在的云OCR也必须单独允许；不可在本地失败时静默外传。OpenAI数据使用与保留条件按实际接口/模型/账号确认；store=false不等于无任何日志或绝对零保留。[T4]

6. 安全与运行底线

上传按白名单、MIME/文件签名/结构组合检查；随机对象键；不信用户文件名作为路径；上传、解析解压大小/条目/页数/时间均有限额。宏、外链、嵌入程序不执行；Excel公式缓存缺失不伪造计算结果，保留原公式和缺失状态。文件安全检验与业务SDK解析不是互相替代。[T5]

原件、预览、下载、学习查询、批量API都按服务端Actor的租户/案件权限检查；用户不能靠传tenant_id切换范围。对已导入HTML邮件去活性内容，不加载远程图片；PDF预览限制主动内容和外链；日志不存API密钥、整份报价或完整模型prompt。

基线建议管理员/一般用户两角色、同一客户工作区共享案件，具体可见范围由客户安全要求确认。先采用成熟认证组件/服务，不自制密码算法。若password方案成立，需安全哈希、会话失效、CSRF防护、安全cookie、频率限制和恢复流程；若指定SSO则仅替换认证Adapter。认证之前不暴露业务API。

后台任务持久化在PostgreSQL，使用短事务领取任务、租约/fencing token/心跳/重试上限。FOR UPDATE SKIP LOCKED可以用于队列争用，但不能代替事务一致性或在整个AI调用期间持有数据库锁。[T6]

重试采取“至少一次执行、幂等提交”模型，不承诺外部AI绝不重复收费。任务失联重取、AI失败、DB提交失败、用户已改数据等均单独处理。文件/案件内容hash不能跨租户公开查重。备份含原件、数据库、学习关系及加密/访问配置；正式上线需实际恢复演练，RPO/RTO与保留期还待客户确认。

7. 与现有SDK的隔离

真实SDK没有在本框架包内安装或核验。DocumentReadPort是本项目自有接口，不是私有SDK公共方法名。W0生成能力映射：PDF文本/页码/渲染、Excel原单元格/原始值/缓存/范围、来源坐标、显式OCR开关、错误与资源上限。

如果SDK缺字段，记录明确的Adapter能力缺口；不以猜测补来源，不偷偷改SDK或第三方模块。最新附件是有限代表的证据预览，不是100K验收，也不证明本项目接入已经通过。该证据边界见 05_依据与未决事项.md。[U4]

02｜纠错学习契约（必须实现）

02｜纠错学习契约（必须实现）

版本：learning-contract-v1。此文件与验收测试同时变更；不能通过替换prompt绕开这些规则。

1. 精确记住什么

原件费目表记：送货钱
AI曾建议：配送料
人工确认：配送费

建立：原件费目表记“送货钱” + 适用上下文 → fee_id(配送费)
禁止仅建立：“配送料” → “配送费”

原表记由source block关联的本次抽取得到；必须把原件表记、AI建议、人工结果分开保存。若原文标签本身是OCR误读或费目/金额边界不明，先修正读取证据；不能把未核对的文本当可信键。

2. 名称、金额、条件分别处理

可复用的内容：费用对应关系、稳定fee_id、适用范围、证据与版本。

不得复用为本次事实：旧单价、旧币种、报价日期/有效期、旧文件位置、旧数量、旧报价是否包含某项。

单价从10改成20不改变名称匹配键。币种变化时分类可以复用，但本次币种必须独立读取并验证，也不得跨币种计算合计。条件中“含安装”与“不含安装”、20尺与40尺、起运地与目的地收费、每票与每柜不能被忽略。

v1精确键

(tenant_id,
 verified_forwarder_id,
 normalize_v1(original_fee_label),
 context_policy_version,
 confirmed_applicability_signature,
 normalization_version)

适用签名v1包含：transport_mode、equipment、billing_unit、charge_scope、extra_terms。UNKNOWN和NOT_APPLICABLE明确分开；UNKNOWN不作通配。原文出现但不能建模的附加条件放入extra_terms，不能删掉。需用独立来源/校验状态确认签名不是模型任意猜测。

初期严格按公司范围确认，不自动把一家公司规则推广到所有公司。同租户其他用户/新案件可复用；其他公司未确认的相似写法由AI提供建议。在真实样本证明可安全泛化后，才版本化增加tenant-wide规则；不要求客户维护该结构。

normalize_v1只做Unicode NFC和空白规范化，保留数字、斜杠、引号、大小写等。任何进一步归一化均需测试和新版本，不在上线后静默重写旧键。键不包含单价/币种/案件ID/文件ID。上下文安全门是内部结果，不能接受客户端提交ready=true作为可信依据。

4. 保存修正的原子操作

  1. 根据已认证Actor取得租户和案件编辑权限，不信请求中的原件名称或tenant_id。
  2. 检查Idempotency-Key及请求hash；相同key同payload返回原结果，不重复学；同key不同payload返回409。
  3. 检查expected_item_version和必要的expected_case_revision，防止覆盖别人或worker已经产生的变化。
  4. 从服务端原始Observation取原表记、source、公司与条件，不能用AI建议字段作为原文键。
  5. 选择已有fee_id或新建概念。客户输入新名称时由服务端处理；同显示名存在时让其选择已有费目，不凭名称自动合并语义。
  6. 检查当前学习键版本expected_memory_version。同一键被他人修改过则409并保留前端输入。
  7. 同一事务更新当前行、行/表版本、correction_event以及learning_version/slot和幂等结果。PostgreSQL并发行为要集成测试，不以SQLite测试替代。[T7]
  8. 返回最新行、费用分组、表版本和学习状态。前端刷新表格，但保留未保存的其他输入；关闭预览不丢输入。

金额-only修正不建立费用名称规则。点击整张表“最终确认”不代表逐条人工审核了每个AI候选，不自动把所有AI输出晋升为已确认映射。费用字段经人工修正/逐项明确确认后才学习；这不增加Master维护流程。

如果资料来源或条件不足，当前修正仍可保存为人工修正，但自动复用状态为NOT_ELIGIBLE，界面明确提示“本次已保存，自动复用尚需确认”，不得显示已学习成功。

5. 冲突与纠正错误记忆

同键出现不同费用目标时，不采用“最后一次写入必然正确”，先记为CONFLICTED。新案件遇到它需要确认，已有已保存案件不自动变化。

在原吹き出し提供“已有不同确认，是否以本次核对结果更新后续识别”的明确提示；只有用户针对该冲突确认，并携带最新memory_version，才能生成替代版本。该动作仍发生在正常业务纠错画面，不引入客户日常Master维护。

撤销是新增版本/事件，不删除历史。撤销后的匹配不能回退找到更早一条ACTIVE。修复规则后，旧案件如需重新整理要显式重算，且先展示与已确认数据的差异，禁止自动覆盖。

6. 费用概念与比较分组

fee_id稳定，display_name是显示名；显示名不能成为唯一业务事实。基本比较键是fee_id + 已验证的适用条件，而非只看中文/日文名称。20尺和40尺可以同一fee_id但不同条件行；“配送及安装套餐”不得直接合并进配送费。

客户可以在吹き出し中选择已有费目实现本次行归类。系统识别出重复概念时给出同画面合并建议，不能自动把历史概念全局合并。全局概念合并属于有版本和审计的操作，当前参考核心不实现；上线前至少保证选择已有费目和本次行重归类可用。

单价表同一公司/条件出现多条费用不能静默覆盖，也不能不经规则相加。保留quote_offer、明细ID和必要的子行/明细展开，后续按客户表样确认显示。

7. AI部分的边界

至少区分两个调用原因：EXTRACTION和CLASSIFICATION。学习命中优化后一类；不可承诺所有已学习文件都零调用。

提取prompt只返回字段值和允许引用的source IDs；分类prompt只返回候选fee_id/新名称、理由、未决条件，不能改本次金额。参考代码的ClassificationPort刻意不提供金额写入接口。

只检索同租户、权限允许、未撤销未冲突的相关案例；不把整个历史库塞入prompt。v1用普通索引/词法相似检索即可，检索结果只作候选。首期不承诺embedding或fine-tuning；增加时走ADR，不可改变精确人工规则优先级。

Structured Outputs约束结构而非正确性；类别ID不在当前允许集合、source IDs越权、返回截断均拒绝或降级为人工确认。[T3]

8. 离线参考核心与正式实现的差别

reference_core实际实现：持久保存精确键、事务纠错、乐观版本、幂等、原文→人工结果、金额保留、scope隔离、冲突和撤销拦截。

它用SQLite，不包含真实认证、source可靠性计算、原件解析、货币/单位业务词典、AI检索/调用、PostgreSQL并发、UI或Excel。Context.ready与Actor由测试可信注入，仅用于核心机制验证；生产不能由客户端填写。reference classify用于新一轮分类决策，旧表显示应读取当前保存数据，不能每次render重算覆盖人工结果。

参考核心的撤销方法是内部调用，无生产HTTP路由；将来路由必须补齐幂等和案件授权。新概念显示名在参考库内采用唯一约束，不能把这条技术简化解释成真实业务永远没有同名不同费目；正式模型以fee_id和条件为准。

5. 纠错请求和响应要点

请求包含：expected_case_revision、expected_item_version、expected_memory_version、Idempotency-Key、修改字段（选择已有fee_id或新名称，二选一）、必要时针对旧学习冲突的明确更新确认。

不得包含可被信任的：tenant_id、原文标签、原件路径、source_ready、condition_verified、任意全局学习scope。可提交用户纠正的业务条件，但其来源和适用性由服务端验证后形成新版本。

服务端返回最新行/表版本、fee_id、warning reasons和learning_effect：

  • ACTIVE：当前已存，后续可在同条件复用。
  • NOT_ELIGIBLE：当前已存，但条件/来源待确认，后续自动复用暂保留。
  • CONFLICTED：当前已存，已有矛盾记录，后续复用暂停。
  • UNCHANGED_AMOUNT_ONLY：只改本次金额，没有建立名称规则。

409版本冲突时不清空用户输入，显示最新值让其核对重提；网络失败时用同Idempotency-Key重试。分类和金额同时改，任一需回滚则整体不成功。学习冲突是明确的保存结果，不伪装成DB异常；DB异常必须回滚。

contracts/reference_correction.schema.json仅对应离线核心的较小请求类型，不含上述完整生产API字段。不能拿它直接生成一个不带case鉴权的公网API。

6. UI契约

登录：依客户认证条件，基线先预留成熟认证Adapter，不自行编密码系统。

A 案件作成：案件名；同案件多文件；邮件正文；选择后开始；处理状态；部分失败可以重试/有理由排除。无Master上传步骤。

B 原価単価一覧：公司/报价方案为列，费用+条件为行；原币种单价；未分类、Included和缺失状态；点击单元格开启吹き出し；来源位置点开侧边只读预览；现场改费用/条件/单价等；保存即刷新；显示学习是否生效；支持补充和排除，不只修改已有黄色格。

按钮初期为「一覧表を保存」「Excelを作成」「Excelダウンロード」。不默认有“新システム用に加工”。保存编辑和下载原件不修改源文件。

C 案件一覧：案件名/担当者/处理状态/待确认数/更新/Excel版本；点开继续。不要用“要確認0”替代全件处理完成。

D 用户：管理员追加/停用；一般用户日常工作。学习结果在本客户允许的业务范围内复用，不局限某个登录人。

7. 状态和输出

文件：RECEIVED → VALIDATING → READING → EXTRACTING → CLASSIFYING → AVAILABLE；异常是FAILED、REVIEW_REQUIRED，主动排除是EXCLUDED且有理由。详细阶段可以合并显示，但后端不可丢失。

案件分别保留ingestion_status（处理完整性）与review_status（业务确认），最终表不靠一个状态字段猜完整性。发布FINAL Excel要求：选定输入均已明确处置、无阻断缺失/冲突、当前revision已经最终确认；DRAFT可输出但文件名/内部页明确“未確認・草稿”，带问题清单，不能作为取込完成证明。

Excel由程序按明确模板生成，文本列写为字符串，不执行以= + - @等开头的原始文本；不嵌外部连接、宏或模型生成公式。保存文本含义同时避免公式注入，需应用端实测。输出保留当前单价和原币种；不做任何未约定的加价/数量/换汇。结构样例不是新系统已接受的规格。

分别报告读取完整性、字段正确性、费目分类、错误复用、未确认数量、修正+原文核对+最终确认时间。黄色比例不等于错误率，模型confidence不等于实测准确率。

  • total_input_documents / succeeded / failed / excluded(reason) / not_processed：总数守恒。
  • independently_expected_lines、found_lines、missing/extra/ambiguous：人工/独立基准照合，不能只从系统已输出行推导完整性。
  • classification_memory_applied_count、eligible_exact_context_count、all_classification_rows：同时报告受限分母与全量分母，不能用小分母夸大自动化。

  • field_accuracy / classification_accuracy：公布定义、样本数和留出方式；不预先承诺95%/100%。
