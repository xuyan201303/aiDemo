# 客户需求分批改修计划（方案评审版）

状态：八项方向已获认可；本文件记录后续改修范围与评审意见。方案认可不代表代码已实现，也不授权处理真实客户资料、运行真实 SDK / OpenAI、修改当前 Demo 数据库或部署。代码实施以后续明确下达的第一批任务为准。不将此前长指令叠加为本计划的实施范围。

客户目标：导入多家フォワーダー的 PDF、Excel、邮件正文报价，生成「原価：単価一覧表」。工作人员纠正费目误识别后，系统记住有依据的原始表记与适用条件，下次遇到相同表记和条件时复用；客户不预先建立或维护费目 Master。例：`OCEAN FREIGHT 20'`、`O/F 20'`、`海上運賃 20'` 经确认后可对应同一业务费目及 20FT 条件。当次单价、币种仍取当次报价。

## 第一批：1. 单条纠错

保留普通整行确认。确认框另给被误归组的**一个明细**明确的纠错入口；操作人可选择已有统一费目，或在本次确认中创建新费目。保存仅改变所选明细的当前归属，然后用现有 canonical comparison projection 重新分组。整行确认接口继续要求当前行的完整成员集合，不通过放松该检查实现单条操作。

单条纠错需要独立的明确命令或契约，校验当前行归属、案件版、明细版、目标 `fee_id` 与名称版、学习记录版及 legacy 学习证据；沿用事务、锁顺序、幂等和显式人工再确认语义。不能只将现有 `/api/items/{item_id}/corrections` 直接接到 UI，因为它不具备整行入口的全部名称版本及 legacy 证据检查。报价单价、币种、原文和既有历史事实不由此操作改写。

验收至少覆盖两类情况：

1. A／B／C 被放在同一行，仅 C 分类错误且它的学习键可与 A／B 区分。只修正 C；A／B 的既有记录不变。下一份 C 报价正确复用修正后的映射，下一份 A／B 报价仍正确复用原有映射。新文件金额分别来自新文件。
2. C 与其他明细共用同一学习键，并且没有可靠业务条件可区分。允许保存 C 的**本次**人工修正；不得静默把共享学习键改成覆盖 A／B 的全局自动规则。学习记录保留冲突或需确认状态；后续 A／B／C 不得被错误地自动归入 C 的费目。没有可区分证据时，不能同时承诺 A／B 与 C 均自动分类。

同时验证撤回后的显式恢复、并发冲突、失败回滚、幂等重放，以及不同 `fee_id` 不因同名合并。检查当前网页和新生成 Excel 的行、名称、价格、币种一致。

## 第一批：5. 三种操作明确分开

保留现有普通整行确认及其直接保存流程，不增加额外弹窗或步骤。把「この明細の分類を修正」与「統一費目名を変更」做成明确不同的入口；输入框文字变化本身不再自动决定共通改名。普通确认和单条纠错只显示本次选定的作用对象。

只有显式进入**共通改名**时，说明同一 `fee_id` 在 20FT／40FT 与其他案件当前显示上的扩大影响范围。共通改名继续使用名称版本控制、追加名称历史、当前 catalog 名称投影，以及现有的 adopted snapshot / correction event 语义；不批量回填未参与明细的历史名称快照。价格和适用条件不随名称改变。不得通过 `_v1`、`_v2` 字面后缀推断身份或版本。

验收：普通整行确认保持原操作；单条分类修正不触发共通改名；显式共通改名才出现影响范围说明，并在保存后让同一 `fee_id` 的当前显示联动，20FT／40FT 仍按条件分行。旧 correction、未参与明细的 adopted snapshot 与历史 Excel 不被改写。

## 第一批：7. 学习状态在网页与 Excel 一致

由同一个服务端判断结果供网页与新生成 Excel 使用，分别表达：本次费目是否确认、来源与条件是否满足学习依据、映射是否已保存并有效、本次是否命中旧确认、是否冲突或撤回。展示文案不能把「可学习」说成「已经学会」，也不能沿用旧规则把满足当前 REAL 学习条件的明细误报为「自動再利用不可」。草稿 / 未完成资料状态与学习状态分别计算。

验收覆盖有效复用、刚人工确认、仅本次确认但不可学习、冲突、撤回及来源不足。逐项核对正常网页状态与新生成 Excel 的「確認情報」「未確認事項」；已生成的旧 Excel 保持原样。比较主表的分组、单价和币种仍使用同一 canonical projection。

## 独立后续批次：2. 适用条件修正

设计 20FT／40FT、billing unit、transport mode、charge scope、extra terms 的人工修正记录。保留原始 `observation`、`source_ref` 和原件，以追加的人工确认层记录修正前后、操作人、时间与原文依据；统一解析当前有效条件，供比较、学习、网页和 Excel 使用。重新评估旧错误签名及现有记忆证据，不直接改旧键或撤销仍有正确证据支持的映射。

本项需要单独评审数据契约、增量迁移和隔离数据库验收。纠正本次条件与以后自动读取类似版式的条件是不同能力，不以费目名称学习冒充版式识别。

## 后续输入与授权扩展：3、4、6

**3. 邮件正文：** 提供正文粘贴入口；原文作为新的文本资料保存，记录内容哈希和可复核的段落 / 字符位置。正文识别、人工确认、学习、比较与 Excel 进入同一业务流程；不能假装成 PDF 或 SDK 来源。无法可靠确定的单价、币种、箱型保留待确认。验收包括新邮件的新价格与旧邮件原文不变。

**4. 报价版式：** 用客户代表资料确定实际支持的 PDF / Excel 结构、表头、箱型布局和排除范围；在应用层评审对 SDK 公共事实的字段映射与证据核验。必要时由操作人确认字段映射，**这只是待确认的实现方式**，并不表示客户已经同意维护版式模板。不直接开发通用模板设计器，不要求客户维护费目 Master。支持范围只依据代表资料和实际验收结果对外说明；扫描件 / OCR 需按实际证据单独评估。字段定位规则与费目表记学习分别保存和验收。

**6. 业务授权：** 在现有三样本 Demo 授权之外设计独立、版本化且受限的业务授权范围。AI 请求、持久预算与可外发的历史费目候选必须遵守同一范围；保留本地记忆优先、未知项才请求分类以及失败 / 超限的明确状态。不能仅删除文件哈希检查或重置既有额度。真实客户资料与真实 AI 使用须以后续明确授权和专门验收为前提。

## 8. 逐批验收及证据规则

第一批就建立独立测试预期，先在隔离环境做写入和错误注入；再在获授权的实际 Demo 部署范围内验证正常网页操作、下一份报价复用和新下载 Excel。真实 SDK / AI 的实际结果、过去已保存的运行证据，与隔离环境注入的错误状态分开标记和留证；注入错误不能宣称是真实模型 / SDK 表现。需要新运行真实 SDK / AI 时，必须另有对应授权；缺少该运行证据的验收项明确标为未完成。

学习验收采用冷启动或可说明的起始状态：独立保存测试预期是允许的，但不得预先向运行学习库写入目标别名答案，再把命中结果冒充本次人工修正产生的学习效果。记录首轮导入、正常网页人工修正、学习事件 / 版本、第二轮新资料命中和本次价格，形成可追踪链。每一批都给出网页、API、Excel、历史不变和未执行项的对应证据；不另建独立 PoC 工程。

全部八项最后的客户场景验收覆盖三种 20FT 表记、20FT / 40FT 条件、不同报价方、不同文件格式、错误归组的纠正与第二轮新报价；输入与外发范围仅按届时获授权的资料和批次执行。未覆盖的真实版式或输入方式不得标记为通过。
